## Executive summary

The API has a focused smoke and critical-workflow test inventory, but coverage
is not measured and the web and mobile clients have no automated test suite.

plus client/API integration behavior for authentication, job discovery,
proposals, contracts, messages, notifications, and reviews.

This report is intended for an implementation agent. It identifies behaviors to
cover; it does not implement or execute tests.

## Prioritized findings

### P0 — API security and data integrity

- Extend route integration coverage for every ownership boundary: client-only
  job mutations, freelancer-only proposal/profile mutations, job-owner proposal
  actions, and participant-only contract/conversation/message access.
- Add negative tests for expired, revoked, malformed, and replayed sessions;
  unavailable accounts; invalid credentials; and password-change session
  invalidation.
- Cover all money boundary cases: unsupported currency, missing currency,
  negative/fractional minor units, invalid budget ranges, and proposal/job
  currency mismatch. Assert that API responses never imply conversion.
- Exercise valid and invalid job, proposal, and contract transitions, including
  repeated acceptance and competing proposals. Assert one contract per job and
  no acceptance after hiring.

### P1 — workflow privacy and history

- Cover notification creation and isolation for proposal, contract, message,
  and review events; users must not read or mutate another user's notifications.
- Cover review eligibility, self-review prevention, duplicate reviews, rating
  bounds, aggregate updates, and review visibility after completion.
- Cover message validation, recipient validation, conversation creation, empty
  history, and unauthorized reads/sends.
- Cover profile and portfolio validation, URL handling, ownership, public
  freelancer visibility, pagination, search, and empty results.

### P2 — client/API integration

- Web pp/src/lib/api.ts: authorization headers, one-time refresh/retry,
  refresh failure session clearing, API field errors, and 204 handling.
- Web primary screens: loading, empty, error, success, and unauthorized states
  for auth, jobs, proposals, contracts, messages, notifications, profiles, and
  reviews.
- Mobile auth/storage/API adapter: secure-store fallback, session restore,
  refresh/retry, logout navigation, network errors, pull-to-refresh, job detail,
  and USD/MMK proposal amount conversion.

## Recommended implementation slice

1. Add isolated API fixtures for two clients, two freelancers, an outsider, and
   an admin; keep database setup separate from development seed data.
2. Add an API acceptance journey from registration through job publication,
   proposal submission, hire, contract completion, messages, and both reviews.
3. Add focused negative-path tests for authorization, money, validation, and
   invalid transitions.
4. Add small adapter/unit tests for web and mobile authentication, refresh, and
   minor-unit formatting/conversion.
5. Add a coverage reporter only after behavioral coverage exists; use it to
   find unvisited branches rather than as the sole quality target.
