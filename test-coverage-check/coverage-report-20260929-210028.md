The latter covers registration, refresh-token rotation, selected money validation, job ownership, duplicate proposals, hiring, participant access, messaging, contract completion, and one review path.

There is no web or mobile test file, test script, or test dependency. No coverage configuration or machine-generated line/branch/statement report was found. `TEST_COVERAGE_REPORT.md` and the older report under `test-coverage-check/` are narrative documents, not measured coverage artifacts. This is therefore a static behavior assessment, not a numeric coverage claim.

The repository also contains persistence models for `Report` and `AuditEvent`, while `api/src/app.ts` registers no report or admin route; this needs an explicit product/implementation decision before coverage can be completed for the admin requirements in `SPEC.md`.

## Prioritized findings

### P0 — Protect identity, authorization, money, and state integrity

1. **Session security has only a refresh-replay assertion.**

   Boundary: `api/src/routes/auth.ts:53-117` and `api/src/middleware/auth.ts:5-21`.

   Add isolated API cases for bad credentials, duplicate registration, inactive accounts, malformed/expired access tokens, expired/revoked refresh sessions, logout, password change, and the requirement that password change revokes all active sessions. Acceptance assertions should use stable status/error codes and confirm old credentials cannot restore a session.

2. **Ownership coverage is too narrow for the number of mutation routes.**

   Boundary: jobs, proposals, profiles, contracts, messages, and notifications routes. Existing tests prove only a subset of job and participant checks.

   Build a caller/resource matrix with two clients, two freelancers, an outsider, and an admin fixture. For every mutation, assert that the wrong owner/participant receives the intended 403 or 404 and that no record changes. Include the public/read routes where inactive or private resources must remain hidden.

3. **Money validation is not covered at the full request boundary.**

   Boundary: `api/src/routes/jobs.ts:7-21`, `api/src/routes/proposals.ts:8-13`, and client conversion in `app/src/pages/dashboard.tsx:22` and `mobile/app/jobs/[id]/proposal.tsx:23`.

   Add table-driven requests for negative, fractional, zero, missing, unsupported, over-limit, reversed-range, USD-cent, and MMK-whole-kyat values. Assert integer `amountMinor` persistence, explicit currency in responses, rejection of mismatched proposal currency, and no implicit conversion.

4. **Lifecycle tests cover one happy path, not the transition graph or race-sensitive hiring rules.**

   Boundary: `api/src/routes/jobs.ts:27-34`, `api/src/routes/proposals.ts:123-166`, and `api/src/routes/contracts.ts:32-56`.

   Add a transition table for each job/proposal/contract status, including terminal states, cancel/close side effects, withdrawn re-submission, and acceptance after hiring. Add a two-request acceptance case and assert one accepted proposal, one contract, one conversation, and no duplicate contract.

### P1 — Protect privacy, reputation, and durable history

5. **Conversation creation accepts references without tested relationship validation.**

   Boundary: `api/src/routes/messages.ts:10-17`; reads/sends are guarded at lines 29-38.

   Add tests for self-recipient, inactive/nonexistent recipient, unrelated `jobId`/`contractId`, duplicate or unrelated participant combinations, empty/whitespace/oversized bodies, and listing isolation. Acceptance should prove that a conversation cannot grant access to a contract or job merely because IDs were supplied by a caller.

6. **Review eligibility is only partially covered and duplicate handling is not specified by tests.**

   Boundary: `api/src/routes/reviews.ts:15-31`, unique constraint `api/prisma/schema.prisma:221`.

   Test both participant directions after completion, outsider and nonparticipant rejection, rating 1/5 boundaries, invalid ratings/comments, duplicate review behavior, and aggregate rating/count updates. Assert a stable client-visible error rather than an unhandled persistence error for a second review.

7. **Notification delivery and privacy have no assertions.**

   Boundary: `api/src/lib/notify.ts:3-20` and event calls in proposals, contracts, messages, and reviews.

   After each event, assert exactly one notification for the intended recipient, no notification leakage to outsiders, and correct target type/id. Test read-one ownership, read-all isolation, idempotence, and empty-user results.

8. **Profiles, portfolio history, and public visibility have no direct tests.**

   Boundary: `api/src/routes/profiles.ts:12-48` and `api/src/routes/auth.ts:119-132`.

   Cover profile field validation, supported currency/hourly-rate boundaries, portfolio URL validation, update/delete ownership, search/availability pagination, inactive profile hiding, and empty results. Include assertions that public responses do not expose password hashes, refresh credentials, or internal error details.

9. **Admin/report/audit requirements are not represented by an API route.**

   Evidence: `Report` and `AuditEvent` models exist, but `api/src/app.ts` mounts only auth, jobs, proposals, profiles, notifications, reviews, contracts, and conversations.

   This is an implementation/contract decision before it is a test task. Once routes exist, add admin-only tests for list/view, suspend/restore, moderation state changes, and audit-event creation; until then, track it as an explicit product gap rather than claiming coverage.

### P2 — Catch client/API integration regressions

10. **Web client behavior is entirely untested.**

    Boundary: `app/src/lib/api.ts:4-20`, `app/src/auth.tsx:6`, and primary pages under `app/src/pages/`.

    Start with adapter tests for auth headers, one-shot 401 refresh/retry, refresh failure session clearing, API field errors, and 204 responses. Add a small screen smoke layer for auth, job discovery/detail/proposal, client job creation, contract/review, messages, notifications, and profile/portfolio flows, including loading, empty, error, and unauthorized states.

11. **Mobile current-slice behavior is entirely untested.**

    Boundary: `mobile/src/api.ts:19-55`, `mobile/src/storage.ts:8-49`, and the current screens under `mobile/app/`.

    Cover SecureStore/localStorage/memory fallback, restore and logout cleanup, network error mapping, one-shot refresh/retry, pull-to-refresh, job empty/error states, and the conversion rule in `mobile/app/jobs/[id]/proposal.tsx:23` for USD cents versus MMK whole units.

## Lean recommended implementation plan

1. Establish isolated API test fixtures and a reset/cleanup strategy that does not depend on development seed data. Include two clients, two freelancers, an outsider, and an admin-shaped fixture once admin behavior is available.
2. Expand the existing critical journey to cover both participants, notifications, both reviews, and message privacy; keep it as one acceptance test rather than duplicating every route assertion there.
3. Add focused API integration groups for authentication/session security, ownership/privacy, money validation, and transition matrices. Prefer request-level assertions because the API is the source of truth.
4. Add small pure/adapter tests for web and mobile session storage, refresh/retry, error parsing, and money formatting/conversion.
5. Add a small client smoke layer for the highest-value screens and state variants. Do not make every visual component a test target.
6. Add a coverage reporter only after behavioral coverage exists, using it to find unvisited branches rather than setting a global percentage as the product goal.
